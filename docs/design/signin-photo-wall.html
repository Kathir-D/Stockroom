0 · Security and privacy posture

The wall renders on the only unauthenticated screen in the application, sourced from a Drive folder that may contain photographs of identifiable students. What follows are requirements, not observations.

Requirement: no client may reach the Drive folder

Enforced by four independent barriers, none of which depends on anyone remembering a rule:

  • The frontend never receives a Drive credential. rclone holds the OAuth token on the Go side; no token is ever serialized into a response. This is CLAUDE.md §4's existing rule, not a new one.
  • The frontend never receives a Drive file ID or a folder listing. It gets opaque local URLs of the form /signin-photos/a4f2…c9.jpg — random tile names with no relationship to Drive.
  • The cache directory cannot be enumerated. fileServer already answers 404 to any request that resolves to a directory, specifically so /files/ cannot be walked as a roster. The same handler is reused here, so the property comes for free.
  • The credential is read-only, and the folder is admin-controlled rather than structural. The remote is configured drive.readonly, so the credential on the machine can read but never modify or delete. It is deliberately not pinned to a single folder with root_folder_id: the admin panel (§7) sets the live folder from a pasted link, so the folder is a runtime value. What bounds it is that only an admin can change it, every change is written to activity_log, and the result is visible in that screen's preview strip before anyone else sees it. The realistic failure here is a wrong link pasted by mistake, not a hostile one — an admin who wanted the roster already has the roster.

There is no code path from the UI back to Google. The wall is a directory of a few dozen JPEGs that exist for about fifteen minutes.

The existing baseline this sits on

  • server/files.go already serves student profile photos over HTTP with no session at all, by design — an <img> tag cannot carry a bearer token. Departmental photography is strictly less sensitive than the roster headshots already served, so this adds no new class of exposure.
  • The server binds 127.0.0.1 (CLAUDE.md §3). The audience is exactly "whoever can stand in front of the machine" — physical access is the access control.
Settled: the source folder may be shared "anyone with the link", and that is accepted. Such a folder is readable by whoever has been forwarded the URL, which is wider than this machine. The owner weighed that and took it: the folder holds department photography the school already circulates, and the exposure exists whether or not this feature is built. It is recorded here as a closed decision rather than a caution on purpose — nothing in this document, in the build order, or in the admin panel asks anyone to go and check the sharing setting, and nobody should add such a prompt later.

What this paragraph used to claim, and what is false: that a link-public folder can be read by rclone with no OAuth at all, so sharing the folder publicly would save the setup step. The only token-free routes to a public folder are a Google Cloud API key, which is more setup than OAuth and needs the Google API client §3 exists to avoid, and scraping the folder's web page, which is worse than not shipping. Residual risks, accepted

  • Normalized tiles sit unencrypted on the machine's disk for minutes at a time. Bounded by the reel design: originals never land on disk, only 900×600 crops, and each is deleted after it is shown.
  • If the machine is screen-mirrored or projected, the wall is on screen. Not a new risk — so is every student name in the browse list.
  • Photos are drawn at random from whatever folder is live, and an admin may replace that folder at any time by pasting a link (§7). Nothing curates the contents, so everything in the live folder will eventually appear on the unauthenticated screen. The admin performing the paste owns that decision, and the preview strip is what makes it checkable before anyone else sees it.

2The reel: prefetch and discard

The reel is a prefetch buffer with single-use contents: a fixed number of tiles are kept ready in advance and deleted once shown. Nothing accumulates on disk, which bounds both storage and the privacy exposure in §0. Here is the state machine.

readynormalized tile on disk, never shownhanded out by the endpoint

The trap worth naming: don't delete on hand-out. When GET /signin/photos returns, the browser has a list of URLs and has not fetched a single image yet. Deleting immediately gives you sixteen 404s and an empty wall. Deletion has to be deferred behind a TTL (default 15 minutes, comfortably longer than the page takes to load and longer than the 10-minute session idle). "Delete after use" means "delete after the batch expires," not "delete after the JSON response."

Mechanics

  • On boot, wipe the directory — but only one the server owns. Every tile is single-use and re-derivable; a leftover from last run is just a photo we already showed, and wiping is also what stops a crash from stranding files forever. The wipe needs a guard, though: see the note below.
  • One goroutine does both jobs, on a short tick (~10s): reap anything expired, then top up while ready < target. One goroutine means no lock dance between the filler and the reaper.
  • Fetches are serialized and rate-limited — one photo at a time, with a small delay. There is no deadline here; the reel refills over minutes and nobody is waiting. Hammering the Drive API to fill a decorative buffer is how a 403 rate-limit gets earned — one that also breaks the nightly backup, since both go through the same rclone remote and the same Google quota.
  • Burst protection. If sign-ins drain the reel faster than it refills, the batch is made up with tiles already handed out that still have at least two minutes to live — a repeated wall rather than an empty one (see "Draining" below). Only when nothing is left at all is the answer []. The frontend also repeats a short list to fill the column rather than rendering a gappy one. Reel exhaustion degrades density, never correctness.
  • Sizing. 48 ready tiles at ~120 KB each is about 6 MB of disk, and at 32 per batch that's a sign-in and a half of runway. The batch was 16 until 2026-09-22 (three sign-ins of runway); it doubled so each column holds sixteen photographs and one comes round every three to four minutes rather than every two. The cost is that back-to-back sign-ins now reach repeats sooner (see "Draining" below), because the refill — about one tile every 20–25 s against a real folder (§10), so roughly 12 minutes for a whole batch — was already the limit, not the buffer. At most 96 tiles are on disk at once, ready and served together — twice SIGNIN_PHOTOS_COUNT, about 12 MB. Before the ceiling, served tiles had no bound of their own.

Draining: the endpoint needs no session

GET /signin/photos is unauthenticated because the screen that calls it comes before anyone signs in, and every call marks up to a batch — 32 — of ready tiles served. As first built, the filler topped the buffer back up whenever fewer than 48 were ready and never looked at how many were out — so hand-outs drove downloads. Anything calling the endpoint in a loop kept the filler fetching a full-size original every two seconds, portraits included (downloaded whole, then refused by §4's gate), on the school uplink and the Google account the nightly backup shares, while the wall was empty for the next person to walk up. The realistic cause is not malice — somebody at the keyboard of the closet PC can do far worse — but a tab stuck reloading the sign-in screen, a kiosk page that refreshes itself, or a script left running. Found in review, 2026-09-22.

The fix bounds the downloads, not the callers:

  • A ceiling on tiles on disk. The filler runs only while fewer than 48 are ready and fewer than 96 exist in total. Served tiles leave only when their TTL runs out, so no number of calls can cost more than 96 downloads per fifteen minutes. The filler resumes by itself as tiles expire. Reaching the ceiling is logged once per episode — normal sign-ins never get there, so that line is how a stuck reload loop gets noticed. The factor is fixed at twice the buffer rather than a new .env variable: one fewer setting to explain, and it follows SIGNIN_PHOTOS_COUNT if that is ever changed.
  • Repeats instead of nothing. When fewer tiles are ready than a batch asks for, TakePhotos fills the rest with served tiles that have at least two minutes left, longest-lived first. A repeat keeps its expiry: it is still deleted on the schedule its first hand-out set, so "delete after use" holds. Only tiles of the current generation are repeated, so a folder an admin has replaced (§7) never comes back through this path. ttl_seconds becomes the shortest life in the batch.

Legitimate use is limited by the refill long before the ceiling: the measured rate on a real folder (one tile every 20–25 s, §10) is about 40 tiles in fifteen minutes, well under 96. With 32 per batch, a second sign-in within about ten minutes of the first gets whatever has been fetched since plus repeats of what is still out — the degradation this section already accepts, and the trade the larger batch makes (§2, "Sizing").

What was not done, and why. Rate-limiting the endpoint to, say, one fresh batch a minute limits the symptom rather than the downloads, and a rush of real sign-ins would hit it before an accidental loop would. Per-client limits have nothing to key on: the server binds loopback, so every caller is 127.0.0.1. And a token issued by the sign-in page is ceremony, since anything that can load the page can fetch the token.

The wipe deletes everything in a path a human typed. SIGNIN_PHOTOS_DIR is an .env value, and "emptied on every start" applied to a mistyped path is a data-loss bug, not a cache policy: pointed at ./uploads by one slip of the finger it would destroy every profile and asset photo on the machine at the next restart, quietly, on a machine whose whole job is to be left running.

So the reel marks the directory it owns. The first time it adopts one it writes a .stockroom-signin-photos file there, and on every later boot it only empties a directory carrying that marker. A directory with contents and no marker is refused: nothing is deleted, the feature turns itself off, and the server logs one line naming the variable to fix. An empty directory is adopted without ceremony, because that is what a fresh install and a fresh t.TempDir() both look like.

The marker is a file rather than, say, requiring the path to end in a known name, because the check has to survive an admin choosing their own path on the closet PC — which the config table invites them to do.

Two files survive the wipe: the marker, and §3's manifest.json. "Wipe the directory" and "build the manifest once per folder, refresh it weekly" were written in different sections and collide in the one directory they share. Taken literally the wipe wins and the manifest is rebuilt on every start — which on a closet PC that gets switched off at night means re-listing tens of thousands of Drive files every morning, for a file whose whole design is that it costs minutes and changes about never. The wipe is about tiles, which are single-use and re-derivable in a second; the manifest is neither, so it is skipped by name. The ownership guard above is unchanged and still refuses a directory holding anything else.

The served directory holds tiles and nothing else

The cache directory ends up holding three kinds of thing: the tiles, the ownership marker above, and §3's manifest.json. §5 mounts that directory on an unauthenticated route. Those two facts were written four sections apart and, put together, are a hole: http.FileServer refuses to enumerate a directory — which is the property §0's third barrier leans on — but it serves any file in one quite happily by name, and the manifest is a listing of every photograph's path inside the Drive folder. §0's second barrier says in as many words that the frontend never receives a folder listing. A flat layout put it one guessed URL away from anyone standing at the machine.

So the tiles live in <dir>/tiles/ and that subdirectory is what §5 mounts (PhotoWall.TileDir()); the marker and the manifest stay in the root, which is served nowhere. The property then holds by construction rather than because §5's handler remembered to exclude a filename — the same reasoning as "every exported method is nil-receiver safe" below, and for the same reason: a rule a handler has to remember is a rule one of them will eventually forget.

Who builds the reel

The reel hangs off DB beside Sessions, but unlike Sessions it is assigned by server/main.go rather than built inside Open, and that is a deliberate departure from the file table in §1.

Open's only way to report a problem is to return an error, and main's only response to one is log.Fatalf — a database it cannot reach is a server that should not start. Routing the photo wall through the same door would make an unwritable cache directory, or a mistyped SIGNIN_PHOTOS_DIR, fatal to the whole API. That directly contradicts §9's invariant: a server that refuses to boot has not merely broken the wall, it has broken sign-in in the most complete way available.

So main calls NewPhotoWall itself, logs a warning on failure and serves without one — the same shape EnsureFailsafeAdmin already has (CLAUDE.md §7), so this is an existing pattern reaching one more feature rather than a new one. Two consequences worth stating:

  • DB.PhotoWall is nil whenever the feature is off, which is the common case and not an error. Every exported method on the reel is nil-receiver safe — TakePhotos on a nil reel returns no URLs and a usable TTL — so §5's handler and §7's screen never branch on it. A nil check that handlers have to remember is a nil check one of them will eventually forget, on the one screen that must never break.
  • The goroutine's lifetime is the signal context, so Ctrl+C stops the reel with everything else.

Tile identity

The filename is random (crypto/rand hex), not derived from the Drive path or a content hash. A content hash would be stable across runs, which quietly defeats "delete after use": the same photo would resolve to the same URL and could be re-requested later from a cached page. Random names make every tile a one-time object.

"One-time" is about the tile's life, not its audience. A drained reel may name the same tile to a second screen inside its TTL ("Draining" above), but never extends that TTL, so the URL still stops existing when its first hand-out said it would.

3Drive access via rclone

rclone is already the decided Drive mechanism for backups (CLAUDE.md §11), so this reuses one token store and one consent flow instead of adding a second. No Google API client code, no OAuth handling in Go.

One-time setup

rclone config
  # n) new remote → name: gdrive → storage: drive
  # scope: drive.readonly     ← read-only. The app never writes to this Drive.
  # root_folder_id: leave BLANK — see below.

# verify the credential works at all
rclone lsd gdrive:

root_folder_id is deliberately left unset on the remote. Pinning it would root gdrive: at one folder, and a remote rooted at one folder cannot read a different pasted one — which is the whole of §7. The live folder is instead a per-invocation parameter, supplied as an rclone connection string so that no command can act on a folder the caller did not name:

rclone lsjson 'gdrive,root_folder_id=<ID>:' -R --files-only …

What is left doing the containing work is drive.readonly: the credential the machine holds can read but never modify or delete anything in the Drive. §0's fourth barrier records that trade honestly.

The manifest

The source folder is large — tens of thousands of files is the assumed scale. The way to stop that from mattering is to separate listing from fetching:

# Built once per folder, then refreshed weekly in the background.
rclone lsjson 'gdrive,root_folder_id=<ID>:' -R --files-only --fast-list --no-modtime
  • Result is written to <dir>/manifest.json — paths and sizes only, no image data. Even tens of thousands of entries is a few MB of text.
  • The first listing of a big folder can take minutes. It runs in the background at startup; until it completes the endpoint returns [] and the sign-in screen is exactly what it is today.
  • A refresh writes to a temp file and renames, so a failed or half-finished listing never replaces a working manifest — the same staged-write discipline photos.go and backup.go already use.
  • It survives a restart. The manifest is read back on boot (the wipe spares it, §2) and is only discarded when it names a folder that is no longer the live one — which is the same stale-folder property §7's generation counter gives at runtime, applied to a server that was stopped when the folder changed.
  • Random selection is a random index into the manifest. No API call to choose, and uniform across the folder.
  • Subfolders are ordinary. -R walks the tree to any depth and lsjson reports a path relative to the folder root, so an entry is events/gala 2026/DSC_0142.JPG rather than a bare filename — and that whole path is what rclone cat is later given, appended to the same connection string. Selection is uniform across every photograph in the tree, not per directory, so a folder holding one shoot of four hundred and six of forty shows mostly the big one. That is the right behaviour for a wall and worth knowing before somebody calls it a bug. A regression test carries a nested path with a space and an uppercase extension from the listing through to the download, because the two halves each had a test and the join between them did not.
Two changes to the command, both made while building it.

The --include glob is gone; the accepted-format list lives in Go. It was going to be spelled twice — once as an rclone pattern and once as whatever the decoder actually supports — and two lists that can disagree is one more thing to keep in step than this needs. Filtering in photowall_drive.go also puts the list in the same file as the code that has to honour it, so adding a format is one edit rather than two, and it removes a dependency on rclone's filter syntax whose failure mode is an empty manifest and no error. The cost is a slightly larger listing to parse, which is text that is streamed and discarded either way.

HEIC left the list. Go has no HEIC decoder — not in the standard library, not in golang.org/x/image — so every .heic in the folder would be a multi-megabyte download that can only ever be thrown away, burning a filler slot and a slice of the same Drive quota the nightly backup draws on. Rejecting it from the listing costs a string comparison. JPEG, PNG and WebP are what is left, and WebP comes from golang.org/x/image/webp, which is the module already pulled in for the resampler rather than a second dependency.

Listing is streamed, and that is what §7 reads

The listing is decoded from rclone's stdout as it arrives rather than buffered and parsed at the end. The memory saving is real but minor; the reason is §7. A large folder takes minutes, the wall is empty for all of them, and an empty wall with no explanation is indistinguishable from a broken feature — so the admin screen has to be able to say rebuilding — 12,400 files listed so far. A running count only exists if something is counting while the process runs, and retrofitting that into a buffered parse would mean writing the listing twice.

Two goroutines, not one

§2 says one goroutine does both of the reel's jobs, so the filler and the reaper never argue over a file being written as it is deleted. The manifest refresher is a second goroutine, on the source, and the rule is intact: it is the only writer of a different file, on a timescale of weeks rather than seconds, and it touches no tile. server/main.go starts the reel first — NewPhotoWall is what creates and adopts the directory the source then reads its manifest out of.

Fetching one photo

rclone cat 'gdrive,root_folder_id=<ID>:<path>' | → stdin → normalizer → tile

cat streams to stdout, so the original is piped straight into the decoder and the full-resolution file never touches the disk. Guard it with a size ceiling from the manifest (skip anything over ~40 MB) and a context timeout, so one pathological RAW doesn't stall the filler. The ceiling is applied when the manifest is built, against the size rclone already reported, so an oversized original costs a line of JSON rather than a download that is then thrown away.

As built, the download is held in memory rather than piped, and is capped at the source. runRclone buffers what rclone prints and the decoder reads the buffer — the original still never touches the disk, which is the property this section is about. The buffer is why the cap has to be on rclone's side: a file that grew after the listing would otherwise be held whole before the normalizer's own 40 MB limit saw it. So the command is rclone cat … --head 41943041, one byte past the ceiling, which is all the normalizer needs in order to refuse it. Added in review.

One call to NextPhoto tries up to four photographs before giving up. §2's PhotoSource contract already put "reject the unusable ones and retry past them" on this side of the seam, and a real folder legitimately holds portraits, panoramas and video that §4's gate turns away; an error out of NextPhoto therefore means "nothing usable right now", which the reel answers by backing off rather than by diagnosing. Bounded at four so a folder of nothing but .mov files returns instead of downloading itself.

4Normalization

Every tile leaves this step as the same 900×600 JPEG, which is what lets the marquee do no layout work and the webview do no scaling work. §12 of the design doc notes the closet PC's webview is not fast; a 12-megapixel JPEG scaled down in CSS is still decoded at full size into memory, sixteen times over.

  1. Read the header only, first

    image.DecodeConfig gives width and height without decoding pixels. Anything failing this is not an image we can use — skip it and move on. rclone lsjson does not expose image dimensions, so this is where the ratio gate has to live.

  2. Honour EXIF orientation — before the ratio test

    This is the step that, skipped, makes the whole feature look broken. A phone photo with EXIF orientation 6 decodes as landscape and must be rotated to portrait. Get the order wrong and a portrait shot passes the 3:2 landscape gate and then renders sideways. Read the orientation tag, apply the rotation, then measure the ratio.

    As built, the tag is split across the pipeline: the measurements are oriented here, the pixels at the end. Taken literally, "apply the rotation, then measure" means turning a twelve-megapixel image — a full second pass and about 48 MB — before knowing whether the file will be used at all, and most of the ones needing a rotation are exactly the ones step 3 is about to reject. So step 2 swaps width and height for orientations 5–8 and step 3 gates on those; the actual rotation happens after the downscale, on the finished 900×600 tile, where it costs half a megabyte. The property the step exists to protect is untouched — the gate never sees a stored shape — and the regression test asserts it from the outside: the same bytes are accepted untagged and rejected tagged 6.

    The tag is read by about a hundred lines of hand-rolled EXIF in photowall_image.go rather than a library, because step 4 names golang.org/x/image/draw as this feature's only new dependency and all it needs from EXIF is one 16-bit number. It fails soft at every step: anything it cannot parse reads as "upright". A camera whose EXIF writer it does not understand should cost one sideways tile in forty, never a wall that quietly stays empty.

  3. Gate on aspect ratio

    3:2 is 1.5. Accept 1.20 – 1.90; reject everything else outright. That admits 3:2 and 16:9 and most 4:3, and rejects panoramas, screenshots, square crops and portrait shots — all of which would either crop to nonsense or force the wall to handle two orientations.

  4. Centre-crop to exactly 3:2, then downscale to 900×600

    Go's stdlib has no resampler; golang.org/x/image/draw with CatmullRom does it and is the only new dependency. Crop before scaling, so the resample runs over the smallest possible pixel count.

    The crop is taken in stored coordinates, which is what lets the rotation wait until the end: a centre crop is centred under all eight EXIF transforms, so the rectangle is the displayed crop's, with its sides swapped back when the orientation swaps axes.

  5. Re-encode as JPEG, quality ~82, and strip metadata

    Re-encoding drops EXIF as a side effect, which is worth having deliberately: original photos carry GPS coordinates, camera serials and timestamps, and none of that should end up in a file served unauthenticated over HTTP. ~120 KB per tile.

  6. Never let one bad file stop the filler

    A truncated download, a HEIC that Go can't decode, a CMYK JPEG — log at debug, discard, pick another manifest entry. A cap on consecutive failures (say 25) backs the filler off so a folder full of .mov files doesn't spin the CPU.

    A rejection is a routine answer, not a fault, so it is a distinguishable one: everything this step turns away is wrapped in one sentinel, which is how the source tells "this file is wrong, try another" apart from "the download broke". HEIC specifically is now kept out of the manifest rather than discarded here (§3), since it can never decode and is never small.

Why the link is never shown back

A Drive folder link is not a label, it is a capability. A folder shared "anyone with the link" is readable by whoever holds the URL, so echoing it into the admin panel puts the entire folder one copy-paste away from anyone who reaches that screen — including anyone standing at a machine left open on it. The project already holds this rule: app_settings.github_token is redacted from the backup export for exactly this reason (CLAUDE.md §11), and password fields are never populated with the existing value. This is that rule reaching one more value, not a new policy.

The folder ID is therefore a secret column. It must be added to the export's redaction list in the same commit that creates it. Missed, the first nightly backup pushes the key to the folder into a GitHub repository — the precise failure §11 already anticipated for github_token.

What the screen shows instead

An admin still needs to know whether the right folder is live. Three things give that without handing back the capability:

  • A name for the folder, not its ID and not its URL. A name is a label: it can be read, but a folder cannot be opened by knowing what it is called.
    As built it is a name the admin types, because the folder's Drive name cannot be fetched. This bullet assumed a lookup that does not exist. rclone addresses Drive by path from a configured root; there is no stat this file id command, and with a bare folder id in hand — which is all a share link yields — there is no way to ask Google what the folder is called without writing the Google API client §3 exists specifically to avoid. Nor can the listing supply it: lsjson returns paths relative to the folder, so the one name it never reports is the folder's own.

    So the paste field has a Name for this folder beside it, and that string is what the status block and the activity_log row carry. This is the honest version of the same affordance — something a person can read that opens nothing — and it costs one more field on a form that is used perhaps twice a year.

    It is required, not optional. A blank label makes both surfaces that depend on it say nothing at all: the screen would report a configured folder with no way to tell which, and the audit row would record that somebody replaced the folder with something unnameable — which is worse than not logging it, because it looks like a log entry.
  • A live preview strip — six tiles currently in the reel, at the same 3:2 the wall uses. This is the real confirmation, because the question an admin actually has is "are the right photographs showing," and it reveals nothing the sign-in screen does not already show to everyone who walks up.
  • Status: configured or not, when the folder last changed and which admin changed it, manifest file count and build time, reel ready/served counts, whether rclone is on PATH, and the last error.

The status says each thing once. "rclone is not installed" and "this server has no Drive source" are the same fact in two wordings — the missing binary is why there is no source — and printing both reads as two problems to fix. The second line is therefore suppressed whenever the first is showing, which is the correction the backup banner already took (CLAUDE.md §13). The rclone check runs per request rather than at boot, so an admin who installs it in response to that line sees the answer change on a reload.

Probe before commit

The paste is validated against Drive before anything is written:

  1. Parse the URL to an ID, or refuse.
  2. Run a bounded listing against that ID with the configured credential.
  3. Refuse on failure, naming what actually went wrong — that folder isn't reachable with the configured Drive account: check it's shared with that account, or set to anyone-with-the-link.

Without this check a typo or an unshared folder returns a success message and the wall silently empties ten minutes later, with nothing on any screen connecting the two events. The probe is the most valuable part of the feature.

"Bounded" is --max-depth 1, and an empty folder passes. Two details the step above leaves open, decided while building it. The depth, because an admin is standing at the screen waiting for the answer and §3's recursive listing of a large folder takes minutes — what is being tested is whether Drive will answer for this id at all, not what is in it. --files-only is deliberately absent for the same reason, so a folder whose photographs all live in subfolders still proves reachable rather than looking empty. And an empty listing is accepted, because §9 already says a folder with no usable photographs is permitted — it may be mid-upload — and refusing it would break the panel in exactly the moment somebody is setting the feature up. What the probe rejects is Drive saying no.

Switching invalidates the reel

A switch is a config write plus a teardown. Doing only the first leaves the wall showing photographs from the folder that was just replaced — the exact outcome this screen exists to prevent. As built it is three steps in this order, each under its own lock rather than one shared mutex — the generation counter below is what makes that safe:

  1. Write the new ID and label to app_settings and the activity_log row, in one transaction.
  2. The source (SetFolder): discard the manifest, cancel any listing of the old folder still running, and nudge a rebuild of the new one in the background.
  3. The reel (Invalidate): advance the generation counter and delete every ready tile. Tiles already served are left to expire on their TTL — their URLs sit in a browser that has already rendered them, and 404ing a live page to save fifteen minutes is the worse trade.

Steps 2 and 3 run only when the folder actually changed. Re-pasting the live link, to rename it or just to be sure, still probes and still writes the new label and its log row, but it is a label edit: tearing the reel down for it would empty the wall for the minutes a refill takes, and every tile thrown away would have been from the right folder. SetFolder always reported "nothing changed" for this case; nothing read the answer until review.

The old folder's listing is cancelled, not waited out. The refresher is one goroutine, so a switch made while the old folder was still being listed used to queue the new folder's listing behind minutes of Drive traffic whose result was then discarded. Worse, if that stale listing failed, its error was filed against the new folder: a red line on the admin screen about a folder no longer in use, and the new folder's first listing pushed behind the five-minute retry gate. A finished listing now checks whether its folder is still the live one before it looks at the error. Both found in review.

The generation counter is what makes this safe under concurrency. A fetch can be in flight when the switch lands; it carries the generation it began under, and a tile whose generation no longer matches is written nowhere and deleted. Without it, a slow rclone cat deposits a photograph from the replaced folder into the new reel minutes later, unreproducibly.

The rebuild is not instant and the screen must say so. A large folder takes minutes to list (§3). Until it finishes the wall is empty and the endpoint returns [] — correct, but indistinguishable from a broken feature unless the screen reports rebuilding — 12,400 files listed so far.

The invariant: no failure in this subsystem may delay, block or visibly break sign-in. The wall is the first thing to go and the last thing to complain.

Settled while running it against a real Drive

Five of the rows above were written before a real folder existed, and the first run against one (2026-09-22, 2,274 files) showed the code honouring the invariant while getting the rows wrong. What changed, and the calls made along the way:

Waiting for the manifest is not failing. The source answered "still being listed" the same way it answered "no internet", and the reel counted both. At one try every two seconds, the minute a first listing takes was 25 failures and a five-minute rest before the listing had finished — and since any failure past the cap buys another rest, the wall came up about twelve minutes after boot on a folder that was ready in one. The source now tags its two normal not-yet states (no folder chosen, listing not finished) so the reel neither counts them nor sets an error, and asks again at the ten-second idle tick rather than every two seconds. A listing that failed, or a folder that holds nothing usable, is still a failure and still counts: that is what keeps a machine with no internet from asking every ten seconds forever. After the fix the first tile arrived 16 seconds after the listing finished.

The admin screen shows the reel's failure only while it is resting. The screen read only the source's listing errors, so a wall with a manifest of two thousand photographs, zero tiles and a resting filler reported nothing wrong at all. It now also reads the reel — but only once a streak has reached the cap, because a single failed download among successes is normal (Drive answered directory not found for a file it had listed a minute earlier, and the same command succeeded four times in a row after) and a red line on a screen whose wall is full is noise. When both have an error, the newer one wins. A streak of ratio-gate rejections gets §9's sentence rather than rclone's: no usable photographs found … only landscape photographs close to 3:2 — anything outside 4:3 to 16:10, which includes every portrait shot, is skipped.

"Logged at debug" became one line per rest and one per recovery. The server has no debug level — every log line is log.Printf — and adding one for a single subsystem would be a second logging convention to keep in step. So nothing is logged per failure, one line is logged at the moment a streak reaches the cap, naming the last cause, and one more when a fetch succeeds again. The second line is an addition to the row as written: without it the last word in the log is "pausing", and whoever reads it next week cannot tell whether the wall ever came back. A full disk and a dropped network take the same path, because both are a fetch that did not become a tile.

An expired sign-in is recognised by rclone's own words. invalid_grant, couldn't fetch token, cannot fetch token or token expired — checked against rclone 1.75.1 with a revoked token rather than guessed. rclone's message already suggests the fix, but names the remote as gdrive-photos{PDhs9}:, its internal name for a connection string, which nobody can type; the warning uses the remote as configured instead. It is logged once per outage and re-armed by any success, so a token reconnected and later expired again is warned about again. Nothing needs restarting, because rclone reads its config on every command. Behind a Photo wall save it is a 503 carrying the fix, not the 400 that tells the admin to check the folder's sharing — the one thing that is fine.

rclone's error messages carried the folder ID, and every one of them reached the admin screen. A failed Drive call quotes the request it made, and that request's query string is '<id>' in parents, URL-encoded. An expired token or a dropped network — the two commonest failures there are — would have put the ID into last_error, which GET /admin/photo-wall returns: the one thing §7 promises no response carries. Found by reading rclone's real output with a revoked token, not by the test that guards §7, which only ever saw the happy path. Every rclone error the wall keeps now passes through one cleaning step that removes the ID in its raw, query-escaped and path-escaped forms, reduces the quoted request to the word Drive, and drops rclone's timestamps and the client-id retirement notice that now opens every message. The cleaning is the photo wall's alone: the backup's runRclone is shared with six backup call sites that carry no secret ID, and changing the text they report was not this section's to do.

10Testing

Consistent with the suite's "one happy path and one gate per module" shape (CLAUDE.md §13). rclone is stubbed behind a small interface so none of this needs a network or a Google account.

Everything down to "backoff" is written and passing, in photowall_test.go, photowall_drive_test.go and photowall_image_test.go — forty-one tests, none of which touch a network, rclone or Postgres. The endpoint's five live in server/photowall_test.go: the empty answer with no wall, reachability with no session or cookie, the batch-then-fetch round trip (which since review also asserts that a second call to a drained reel gets the first batch back, still fetchable), the manifest and the marker unreachable through the mount, and /files/ still working after fileServer grew its prefix. §7's five — link parsing, the probe gating the write, the ID never leaving the server, switch-invalidates, preview-does-not-consume — are written and passing too, in photowall_admin_test.go, joined by three more the build turned up as worth having: every one of the four admin calls is admin-only, the off state does not panic, and the probe does not fall through to the recursive listing. Two more sit at the HTTP boundary in server/photowall_test.go: the four routes refuse a student and never name a folder_id, and three previews over HTTP leave the reel untouched.

The first half of the manual pass was run on 2026-09-22 and found four defects the suite could not have: the listing crash, the twelve-minute warm-up, the reel's failures reaching no screen, and the folder ID in rclone's errors (§9). Each fix has a test, and each test was checked by breaking its fix and watching it fail. Still outstanding: pulling the network, and a full cycle in the Wails window on the slowest machine available.

  • Normalizer, happy path — a 3000×2000 JPEG comes out exactly 900×600.
  • Ratio gate — a 1:1 and a 21:9 are rejected; a 4:3 is accepted and cropped.
  • EXIF orientation — a portrait tagged orientation 6 comes out upright, and is then rejected by the ratio gate rather than emerging sideways. This is the regression that matters most.
  • Metadata stripped — an input with a GPS tag produces an output with none.
  • Reel lifecycle — fill to target, take a batch, assert the files still exist immediately after (the delete-on-hand-out bug), advance the clock past the TTL, assert they're gone and the reel refilled.
  • Concurrent take — two goroutines taking batches never receive the same tile ID.
  • Boot wipe — a marked directory seeded with junk, including a subdirectory, is empty after startup, and the marker survives.
  • The wipe refuses a directory it does not own — a folder holding a profile photo and no marker returns ErrInvalid, names SIGNIN_PHOTOS_DIR, and leaves the photo on disk. An empty directory, and a path that does not exist yet, are both adopted. This is the test standing between a typo and every photo on the machine.
  • Endpoint — 200 with [] when unconfigured, and reachable with no session or cookie.
  • A nil reel is not a crash — TakePhotos and Invalidate on the off state return empty and do nothing, because that is the state most of this code runs in.
  • Config refuses a typo — SIGNIN_PHOTOS_COUNT=none, =0 and =-4 each stop startup with the variable named, rather than falling back to the default where nobody would ever notice.
  • Backoff — the filler rests after 25 consecutive failures and one success clears the record, so a transient outage does not leave the reel idle for five minutes after the network returns.
  • Link parsing — every accepted form in §7 yields the same ID; a Docs URL, a file URL and free text are refused. Also refused, found while writing it: a drive.google.com URL with no folders segment at all, and an id too short to be one.
  • Probe gates the write — an unreachable folder leaves app_settings unchanged and the previous folder live.
  • The ID never leaves the server — assert the GET and PUT response bodies contain neither the folder ID nor any drive.google.com string. This is the test that keeps the privacy property from quietly regressing when someone later adds a debug field.
  • Switch invalidates — fill the reel, switch, assert every ready tile is gone, served tiles survive, the manifest is discarded and the generation advanced.
  • Preview does not consume — two preview calls leave the tiles ready and still available to /signin/photos.
  • The listing as rclone actually prints it — every field present, and ModTime an empty string. Under --no-modtime rclone still prints the key; every other fixture left it out, which is the one shape rclone never produces, so the suite passed while the first real listing failed on its first line. The listing now decodes into its own three-field struct rather than the backup's, whose time.Time refuses "" and which lists without that flag.
  • Waiting for the manifest is not failing — twice the cap's worth of "still listing" leaves the reel with no failures, no error and nothing logged, and the first try after the manifest lands a tile. The source side is its own test: no folder and an unfinished listing are tagged as warming up, a failed listing and an empty folder are not.
  • One line per rest — seventy-five failures log exactly one line, naming the cause; the next success logs exactly one more.
  • The admin screen explains a resting reel — 24 failures show nothing, the 25th shows the 3:2 sentence for a ratio streak and "paused" with the cause for anything else.
  • Errors never carry the folder ID — rclone 1.75.1's own text for a revoked token and a dropped network, with the ID in the request URL and bare in a 404, through a download, a listing and the probe: none of it reaches an error, the status or the log. The expired sign-in names rclone config reconnect gdrive:, is warned about once over three failures, and again after a success re-arms it.
  • The ceiling bounds downloads — a hundred hand-outs against a four-tile buffer cost exactly eight downloads, log the ceiling once, and the reel refills normally once the TTL passes.
  • A drained reel repeats — the second batch is the first one's tiles, reporting the ten minutes they have left in both ttl_seconds and the tile's max-age. They are still deleted on the first schedule, and a tile with under two minutes left is not handed out.
  • A replaced folder is never repeated — after Invalidate, the served tiles of the old generation are not handed out again.
  • Tile max-age — a ready tile gets the full TTL, and an unknown name or a nil reel gets 0. The ceiling test and the replaced-folder test were checked by removing their guard and watching them fail.
  • Re-pasting the live folder keeps the reel — added in review. A label-only save leaves every ready tile and the generation where they were, and the new label is what the status reports.
  • A switch cancels the listing it replaces — added in review. A listing blocked on Drive returns as soon as the folder changes, leaves no error behind, and the new folder is due immediately rather than after the retry gate. Both tests were checked by reverting their fix and watching them fail.
  • Manual, on the real Drive — run the manifest build against the actual folder and time it; confirm the reel fills; pull the network cable and confirm sign-in is untouched; watch the wall in the Wails window for a full cycle on the slowest machine available. Done 2026-09-22 on the development machine, up to the network pull: 2,274 files listed and 2,073 kept in about 60 s cold and 22 s warm; the first tile 16 s after the listing; tiles exactly 900×600, 54–109 KB, no GPS; a batch of 16 over HTTP with the tile served private, max-age=900 and the manifest a 404 through the mount. The reel fills at roughly one tile every 20–25 s — sixteen in the first six and a half minutes, so about twenty minutes to 48. Not a failure mode (§9's drained-reel row covers it), but the obvious next speed-up: every fetch is a fresh rclone cat resolving the path folder by folder, and a portrait is downloaded in full before the gate refuses it.

11Build order

Backend first. Each step is independently verifiable, and the frontend is an afternoon once the endpoint returns real URLs.

  1. Config + directory + boot wipe built

    Five Config fields, NewPhotoWall called from server/main.go, the cache dir created, marked and cleared at startup. Verified: the server starts, the directory appears, junk in it disappears, and a directory holding anything the server did not write is refused with the files intact and the API up.

  2. rclone remote, by hand done

    rclone config with drive.readonly and root_folder_id left blank (§3); confirm rclone lsjson 'gdrive,root_folder_id=<ID>:' -R --files-only lists the intended folder. The folder's sharing setting is not checked here or anywhere else — §0 closed that question. Done on the development machine 2026-09-22 as gdrive-photos, on rclone's shared client id, whose retirement during 2026 is tracked in CLAUDE.md §13 rather than here. The closet PC needs the same step.

    Background, staged write, weekly timer, streamed listing with a running count, reload after a restart, and SetFolder so §7's switch has something to call. rclone sits behind two function fields, so the tests need neither the binary nor an account.
